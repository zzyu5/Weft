WHY THIS BATCH
--------------
batch2b (0ca224f7) was ruled INVALID (裁决一.1): the two head-to-head-timed
vec_dot objects were built by an ASYMMETRIC toolchain — OURS = clang-17 -O2
(tcrv-translate's embedded LLVM-20 codegen export) vs FACTORY = gcc -O3 (ggml
own object). ratio=factory/ours therefore conflated KERNEL quality with
COMPILER/-O quality. batch2c rebuilds BOTH timed objects with ONE identical
compiler + flags + march, so the ratio isolates CODE difference, not compiler
difference. The mechanized fairness pre-flight (PREFLIGHT(0)) is the gate.

TOOLCHAIN SELECTION (symmetric) + RATIONALE
-------------------------------------------
Directive named "gcc-12.3.1 -O3". On THIS board that specific compiler is NOT
usable for either side:
  * system gcc 12.3.1 (openEuler, /usr/bin/gcc, /usr/bin/cc) has NO
    riscv_vector.h and rejects _Float16 ("not supported on this target") and
    the `zvfh` march token — it cannot compile ggml's RVV path NOR our EmitC C.
  * clang-17 compiles basic RVV but LACKS the segment/tuple intrinsics ggml
    arch/riscv/quants.c needs (e.g. __riscv_vcreate_v_*) — cannot build factory.
The RVV + fp16 + tuple-intrinsic capable toolchains actually installed are
gcc-15.2.0 (SpacemiT fork) and llvm-18. Chosen SYMMETRIC compiler for BOTH
timed sides:
    riscv64-unknown-linux-gnu-gcc/g++ (GCC) 15.2.0
    /opt/tcrv-toolchains/gcc-15.2.0/bin/
    flags: -O3 -march=rv64gcv_zfh_zvfh_zba_zbb_zbs -mabi=lp64d
           -ffunction-sections -fdata-sections
This fully satisfies the compliance PRINCIPLE (same compiler + same -O + same
march on both timed objects → isolates code diff, not compiler diff). It also
satisfies the task's "gcc" intent; only the version differs from the (on this
board non-existent for RVV) 12.3.1.  march=<full zvfh> = rv64gcv_zfh_zvfh_zba_
zbb_zbs (zba/zbb/zbs added so MARCH covers the board ISA for the harness
march-complete gate; zvfhmin/zfhmin implied). ours + factory .comment are
BOTH exactly "GCC: (GNU) 15.2.0" and their Tag_RISCV_arch strings are BYTE-
IDENTICAL (verified in PREFLIGHT(0) below).

LINK / DRIVER compiler (uniform, NON-biasing): clang-17. The gcc-15.2.0 cross
toolchain ships no libgomp.spec (bare cross-gcc), so it cannot satisfy the
harness's unconditional -fopenmp link flag; the system gcc-12.3.1 rejects the
zvfh march. clang-17 accepts the march + supplies libomp for -fopenmp + links
the gcc-built objects cleanly. Per the harness design (PREFLIGHT(3)) the link/
driver compiler is applied UNIFORMLY to the whole exe and does NOT touch the
ours/factory kernel machine code (both are pre-built .o); per-side symmetry is
sealed by PREFLIGHT(0) on the ACTUAL timed objects. This is exactly the intended
separation (timed-object compiler ≠ link compiler), not an asymmetry.
