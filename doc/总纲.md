## 一、项目是什么

Weft 是 **Intent Kernel DSL 的 RISC-V domain realizer**。

Intent 是一个 Python-hosted、结构化张量流（structured tensor-flow）的 kernel
DSL：用户在 `@intent.kernel` 里写出完整的算子算法——逻辑索引域、
`reduce`/`scan`/`contract`/`state_stream`/`group_by`/`gather`/`scatter` 等结构化
原语、carry state、runtime control flow——但**不写** `program_id`、tile 大小、
grid、寄存器/共享内存布局、pipeline stage 这些"machine realization"细节。
Intent 语言规格本身跨多个后端：GPU 一侧已有 Triton/TileLang/cuTile 承接
"从 Intent kernel 到具体 GPU 指令"的 realization；**RISC-V 一侧没有对应物，
这正是 Weft 存在的理由**。

Weft 不做 GPU，不自建第二个 GPU owner，不与 Triton/TileLang/cuTile 竞争。
Weft 的唯一职责：把 Intent kernel 的结构化算法，编译成 RISC-V domain 内
（RVV 向量扩展 / IME 矩阵类扩展 / Scalar 无向量兜底，以及未来任何新增的
RISC-V 扩展）某个 owner 的具体、正确、高质量的机器代码。

## 二、研究问题

> 给定一个用结构化原语（而非预先注册的封闭算子目录）表达的开放算子算法，
> 编译器能否在不向用户暴露 tile/寄存器/LMUL 等硬件调度参数、不依赖开放式
> 在线搜索或人工试探的前提下，用 capability-driven 的解析构造方法，为一个
> 内部异构（多 typed owner 共存）的 target domain 推导出合法且具有专家级
> 质量的 Physical Plan 与最终 kernel？

## 三、两条不可动摇的本质

一切具体设计（结构消费契约、owner 选择规则、Physical Plan 推导公式、
测试哲学）都要向这两条负责，不为了别的目标牺牲它们：

1. **可扩展性（Extensibility）**——新增结构化原语组合、新增 RISC-V 扩展
   （新 owner）、新增硬件能力事实，主要局部增量接入；不要求为每种
   算子×格式×硬件组合手写一份完整实现。
2. **在可扩展性之上的高性能（Performance on top of extensibility）**——
   声明式/可组合的设计不能把专家级硬件知识压扁成最小公分母。每个 owner
   仍必须能表达自己最专的招数（RVV 的 `vfmsac`/`vrgather`/LMUL 折叠，IME 的
   矩阵类指令，等）。

## 四、系统边界（什么不做）

- 不做 GPU construction owner、不做 GPU capability/body/artifact；GPU 由
  Intent 自己的架构交给 Triton/TileLang/cuTile 解决。
- 不做通用图级/端到端模型编译；输入边界止于单个 Intent kernel（一个
  `@intent.kernel` 对应一次编译）。
- 不做开放式在线 autotuner/cost-model 搜索；Physical Plan 的选择必须是
  capability-driven 的解析构造 + legality-first 的候选过滤，qualified
  measurement 只能在合法候选集内做残差修正，不创造候选、不绕过合法性。
- 不向用户暴露 tile/LMUL/warp/寄存器等硬件调度参数；这些是 `I.auto(...)`
  占位，完全由 Realizer 决定，且对用户/上层不可观察。
- 不假设"结构层"可以统一驱动 RVV 与假设中的其它执行模型的具体指令选择；
  跨 owner 统一止步于 Intent 已经提供的迭代空间几何，指令选择/内存映射/
  同步原语必须留给 owner-local 专化。

## 五、总体数据流

```text
Intent kernel source（结构化原语 + 纯值表达式 + 控制流 + effects）
  → Weft front-end 契约消化（模块 A）
  → RISC-V domain binding + capability 环境（模块 B）
  → 每个结构化原语实例：owner 候选构造 + legality（模块 C）
  → 选中 owner 内：Physical Plan 解析推导（模块 D）——核心研究贡献
  → 跨层嵌套一致性 + auto 不可观察性校验（模块 E）
  → typed extension body 构造（模块 F）
  → artifact/机器码发射（模块 G）
  → 正确性与证据（模块 H）
```

各模块的目标、输入输出契约、关键未决问题见 `doc/modules/`。

## 六、当前状态

本文档与整个 `doc/` 目录记录的是**目标态设计**，不是已完成实现。截至本文档
建立时：

- 旧架构（RVV-only、9 个手写问题类型、5 个独立 dequant mechanism）的代码
  资产（`lib/Plugin/RVV/` 等）仍在仓库中，尚未按新设计重写或验证是否可以
  复用/迁移——这是模块 F/G 需要回答的问题，不是默认答案。
- 模块 D（Physical Plan 解析推导）是全新研究问题，没有可直接套用的先例；
  模块 A/C/E 需要从"封闭问题目录"改造为"开放结构组合空间"，也是新工作。
- 具体的验证算子、里程碑顺序尚未确定；`doc/modules/*.md` 中列出的是模块
  边界与关键问题，不是排期。
